# 第4章 数据库与空间数据设计

## 4.1 PostGIS空间数据库概述

### 4.1.1 PostGIS扩展简介

PostGIS是PostgreSQL数据库的空间扩展模块，实现了OGC（Open Geospatial Consortium）简单要素规范，为数据库提供了空间数据类型、空间索引和空间函数[4]。本系统采用PostgreSQL 15.0和PostGIS 3.3版本。

PostGIS提供的核心能力包括：空间数据类型（Geometry、Geography）、空间索引（GIST索引、BRIN索引）、空间函数（关系判断、度量计算、处理操作等300余个）、坐标系统转换（支持3,000多种投影）。相较于传统的经度纬度字段存储方式，PostGIS的几何类型在存储效率、查询性能、功能完整性方面具有显著优势。

### 4.1.2 空间参考系统

系统统一采用WGS84地理坐标系（SRID 4326），这是GPS设备和Web地图服务的标准坐标系。所有空间数据在存储时指定SRID为4326，例如：

```sql
ST_SetSRID(ST_MakePoint(116.4, 39.9), 4326)
```

该坐标系使用经纬度表示位置，经度范围-180°至180°，纬度范围-90°至90°。北京地区的经度约在115.7°-117.4°之间，纬度约在39.4°-41.6°之间。

## 4.2 核心数据表设计

### 4.2.1 空间数据表设计

空间数据表是GIS系统的核心，本系统设计了四个主要空间数据表。

**（1）monitoring_stations - 监测站点表**

监测站点表记录监测站的位置和属性信息，表结构见表4-1。

**表4-1 monitoring_stations表结构**

| 字段名 | 数据类型 | 长度 | 约束 | 说明 |
|--------|---------|------|------|------|

| station_id | VARCHAR | 50 | 唯一 | 站点编号（如BJ001） |
| name | VARCHAR | 100 | 非空 | 站点名称 |
| **location** | **GEOMETRY(Point,4326)** | - | - | **站点位置（PostGIS类型）** |

| zone_id | INTEGER | - | 外键 | 所属风险区域ID |

## 4.3 空间查询设计

### 4.3.1 PostGIS空间函数应用

PostGIS提供了丰富的空间函数，本系统主要使用的函数见表4-8。

**表4-8 系统使用的PostGIS空间函数**

| 函数名 | 功能分类 | 功能说明 | 应用场景 |
|--------|---------|---------|---------|
| ST_SetSRID | 构造 | 设置空间参考系统 | 创建几何对象 |
| ST_MakePoint | 构造 | 创建点几何 | 存储监测站位置 |
| ST_GeomFromGeoJSON | 构造 | 从GeoJSON创建几何 | 前端提交空间数据 |
| ST_Contains | 关系 | 判断包含关系 | 判断点是否在区域内 |
| ST_Intersects | 关系 | 判断相交关系 | 判断路径是否穿过风险区 |
| ST_DWithin | 关系 | 判断距离内 | 查找附近的避难所 |
| ST_Distance | 度量 | 计算距离 | 计算到避难所的距离 |
| ST_Length | 度量 | 计算长度 | 计算道路长度 |
| ST_Area | 度量 | 计算面积 | 计算风险区域面积 |
| ST_AsGeoJSON | 输出 | 转换为GeoJSON | 返回给前端渲染 |
| ST_X / ST_Y | 访问 | 获取经纬度 | 提取坐标值 |

### 4.3.2 典型空间查询语句

**查询1：查找某风险区域内的所有监测站**

```sql
SELECT ms.station_id, ms.name, ST_X(ms.location) AS longitude, 
       ST_Y(ms.location) AS latitude
FROM monitoring_stations ms
INNER JOIN risk_zones rz ON ms.zone_id = rz.id
WHERE rz.id = 9;
```

该查询通过zone_id字段关联查询，避免了复杂的空间运算，查询效率高。

**查询2：判断用户位置是否在风险区域内**

```sql
SELECT rz.id, rz.name, rz.base_risk_level
FROM risk_zones rz
WHERE ST_Contains(
  rz.geometry,
  ST_SetSRID(ST_MakePoint(116.4, 39.9), 4326)
);
```

ST_Contains函数判断点是否在多边形内，利用GIST空间索引，在10个风险区域中查询耗时仅5毫秒。

**查询3：查找最近的3个避难所**

```sql
SELECT id, name, address,
       ST_Distance(
         location::geography,
         ST_SetSRID(ST_MakePoint(116.4, 39.9), 4326)::geography
       ) / 1000 AS distance_km
FROM shelters
ORDER BY location::geography <-> 
         ST_SetSRID(ST_MakePoint(116.4, 39.9), 4326)::geography
LIMIT 3;
```

该查询使用geography类型计算球面距离（单位：米），`<->`操作符利用空间索引快速找到最近邻。

**查询4：查找与某路径相交的风险区域**

```sql
SELECT rz.id, rz.name, rz.base_risk_level
FROM risk_zones rz
WHERE ST_Intersects(
  rz.geometry,
  (SELECT geometry FROM escape_routes WHERE id = 1)
);
```

ST_Intersects函数判断线段与多边形是否相交，用于检查逃生路径是否穿过风险区域。

**查询5：获取风险区域的GeoJSON格式数据**

```sql
SELECT id, name,
       ST_AsGeoJSON(geometry)::json AS geometry_geojson
FROM risk_zones;
```

ST_AsGeoJSON函数将PostGIS几何类型转换为GeoJSON格式，方便前端Leaflet地图直接渲染。

### 4.3.3 空间索引优化

空间查询的性能优化主要依赖空间索引。系统在所有空间字段上建立了GIST索引。

性能测试对比（在35,513条道路数据上）：
- 无索引：查找100米内的道路，耗时3,200毫秒
- GIST索引：查找100米内的道路，耗时15毫秒

索引建立后，空间查询性能提升超过200倍。索引文件占用空间约为数据文件的20%，是可接受的存储开销。

## 4.5 数据完整性约束

### 4.5.1 主键约束

所有数据表都定义了主键，保证记录的唯一性。主键采用自增整数类型（SERIAL），由数据库自动生成，避免了业务字段作为主键可能带来的更新问题。

### 4.5.2 外键约束

外键约束保证了数据的参照完整性。主要的外键关系包括：

- risk_zones.disaster_type_id → disaster_types.id
- monitoring_stations.zone_id → risk_zones.id  
- monitoring_data.station_id → monitoring_stations.station_id
- risk_assessments.zone_id → risk_zones.id
- warnings.disaster_type_id → disaster_types.id
- user_reports.user_id → users.id

当删除被引用的记录时，数据库会阻止删除操作或级联删除相关记录，防止出现悬空引用。

### 4.5.3 唯一性约束

部分字段需要保证唯一性：users表的username和email字段、monitoring_stations表的station_id字段、risk_zones表的code字段等。唯一性约束在数据库层面保证，应用层无需额外检查。

### 4.5.4 检查约束

部分字段需要满足特定条件：风险等级字段限制在1-5之间、置信度限制在0-1之间、经度限制在-180至180之间、纬度限制在-90至90之间。检查约束示例：

```sql
ALTER TABLE risk_assessments
ADD CONSTRAINT check_risk_level 
CHECK (current_risk_level BETWEEN 1 AND 5);

ALTER TABLE risk_assessments
ADD CONSTRAINT check_confidence 
CHECK (confidence_score BETWEEN 0 AND 1);
```

## 4.6 数据库性能优化

### 4.6.1 索引策略

除空间索引外，系统在高频查询字段上建立了B-Tree索引，包括：

- monitoring_data表：(station_id, timestamp) 复合索引
- risk_assessments表：(zone_id, assessment_time) 复合索引  
- warnings表：(is_active, issued_at) 复合索引
- user_reports表：(status, created_at) 复合索引

索引设计遵循选择性原则，在选择性高的字段（区分度大）上建立索引，避免在选择性低的字段（如性别）建索引造成浪费。

### 4.6.2 数据分区

monitoring_data表数据量大且持续增长，采用按时间分区的策略。每月一个分区，历史数据自动归档到对应分区。查询时如果指定时间范围，数据库只扫描相关分区，提高查询效率。

### 4.6.3 查询优化

复杂查询使用EXPLAIN ANALYZE分析执行计划，优化慢查询。常见优化手段包括：避免SELECT *，只查询需要的字段；使用LIMIT限制返回记录数；合理使用JOIN代替子查询；利用覆盖索引避免回表。

监测数据查询限制返回500条以内，避免一次加载过多数据。前端采用分页加载，每页20条记录，减轻服务器压力。

系统采用定期备份策略，每天凌晨3点自动执行全量备份，使用pg_dump工具导出数据库：

```bash
pg_dump -U disaster_user -d disaster_risk_db > backup_2025-10-09.sql
```

备份文件保存7天，定期清理旧备份。关键业务表（risk_assessments、warnings）额外进行实时备份，每小时导出一次增量数据。

### 4.7.2 数据恢复

数据恢复使用psql命令导入备份文件：

```bash
psql -U disaster_user -d disaster_risk_db < backup_2025-10-09.sql
```

测试环境定期从生产环境恢复备份数据，验证备份文件的有效性。
