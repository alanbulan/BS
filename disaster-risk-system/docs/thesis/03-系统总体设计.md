### 3.1.2 技术选型

技术选型遵循成熟度高、社区活跃、易于开发的原则。表3-1列出了主要技术选型及其理由。

**表3-1 系统技术栈**

| 层次 | 技术框架 | 版本 | 选型理由 |
|------|---------|------|---------|
| 前端Web | Vue 3 + TypeScript | 3.5/5.9 | 响应式设计、组件化开发、类型安全 |
| 前端Web | Element Plus | 2.10 | 丰富的UI组件、文档完善 |
| 前端Web | Leaflet | 1.9 | 轻量级地图引擎、插件丰富 |
| 前端Web | ECharts | 6.0 | 强大的图表库、支持多种图表类型 |
| 前端Mobile | React Native + Expo | 0.79/53 | 跨平台开发、原生性能、开发效率高 |
| 后端 | Node.js + Express | 20/4.18 | 事件驱动、高并发、生态丰富[13] |
| 数据库 | PostgreSQL + PostGIS | 15/3.3 | 空间数据扩展、查询性能优异[4,5] |
| ML服务 | Python + FastAPI | 3.10/0.104 | ML库丰富、异步高性能 |
| ML算法 | scikit-learn | 1.3 | 随机森林实现、API简单[2,3] |

选择PostgreSQL+PostGIS的原因在于其提供了完整的空间数据类型（Point/LineString/Polygon）和丰富的空间函数（ST_Contains、ST_Distance、ST_Intersects等），支持空间索引（GIST索引），查询性能优于传统数据库的坐标字段存储方式。

选择Node.js作为后端框架，其基于事件循环的非阻塞I/O模型适合处理大量并发请求，在高并发场景下响应速度优于传统的同步阻塞模型[13]。

### 3.1.3 模块划分

系统按照功能职责划分为9个主要模块，各模块职责明确，相对独立。

**用户管理模块**：负责用户注册、登录、权限控制。实现JWT认证机制，生成和验证访问令牌。管理用户的基本信息、角色分配、权限设置。

**监测管理模块**：管理20个监测站点的基本信息，包括站点位置（PostGIS Point类型）、站点类型、所属风险区域。管理10种类型的监测数据，实现数据的自动生成、存储、查询和可视化展示。

**风险评估模块**：系统的核心模块。管理10个风险区域的空间数据（Polygon类型），实现单区域评估和批量评估功能。调用机器学习服务获取智能预测结果，存储和展示历史评估记录。

**预警管理模块**：根据风险评估结果生成预警信息，管理预警的级别、范围、内容、有效期。实现预警的地图展示和移动端推送。

**路径规划模块**：基于35,513条OpenStreetMap道路数据，实现A*路径规划算法[8]。支持最短、最快、最安全三种模式。提供Web端路径展示和移动端GPS导航功能。

**避难所管理模块**：管理11个避难所的位置、容量、设施信息。实现就近推荐和导航功能。

**灾害上报模块**：公众通过移动端上报灾害信息，包括照片上传、GPS定位、描述填写。管理员可在Web端审核上报信息。

**地图可视化模块**：在Web端使用Leaflet框架渲染多图层地图，在移动端使用React Native Maps实现地图交互和GPS定位。

**系统配置模块**：管理系统运行参数，包括预警阈值、紧急联系人、数据清理策略等。配置信息存储在system_config表，支持动态调整。

### 3.2.2 空间数据流

空间数据在系统中的流转涉及多种几何类型。监测站位置使用Point类型存储经纬度坐标；风险区域边界使用Polygon类型存储多边形顶点序列（21-38个顶点）；道路使用LineString类型存储路径点序列；逃生路径计算后也以LineString形式存储。

PostGIS在空间数据查询时自动使用GIST索引，大幅提高了查询效率。例如查询某点是否在风险区域内，使用ST_Contains函数，在10个风险区域中查询耗时仅5毫秒。

## 3.4 数据库设计概要

### 3.4.1 数据库选型

数据库选型考虑了空间数据支持、查询性能、扩展性三个关键因素。表3-5对比了三种主流数据库方案。

**表3-5 数据库选型对比**

| 数据库方案 | 空间数据支持 | 空间函数数量 | 查询性能 | 社区活跃度 | 学习成本 | 选择结果 |
|-----------|-------------|------------|---------|-----------|---------|----------|
| MySQL + MyGIS | 基础 | ~50个 | 中 | 高 | 低 | ❌ |
| MongoDB | 基础 | ~20个 | 高 | 高 | 中 | ❌ |
| **PostgreSQL + PostGIS** | **完整** | **300+** | **高** | **高** | **中** | **✅** |

PostGIS是PostgreSQL的空间扩展，完全实现了OGC简单要素规范（Simple Features），提供Point、LineString、Polygon等几何类型，支持坐标系统转换、空间关系判断、缓冲区分析等功能，是目前最成熟的开源空间数据库解决方案。

系统共设计18个数据表，按功能分为五类，如表3-6所示。

**表3-6 数据库表分类**

|------|--------|-----------|--------|------|

| 监测数据表 | 2 | monitoring_data, monitoring_station_types | 19,410 | 高频更新 |
| 评估预警表 | 2 | risk_assessments, warnings | 31 | 业务核心数据 |

各服务之间通过JSON格式交换数据。Backend和ML服务都可直接访问PostgreSQL数据库，但遵循不同的数据访问模式：Backend负责写操作和复杂业务查询，ML服务只读取监测数据用于预测。

## 3.6 安全设计

### 3.6.1 认证授权机制

系统采用JWT令牌机制实现用户认证。用户登录时，服务器验证用户名和密码，验证通过后生成包含用户ID和角色信息的JWT令牌，令牌有效期为24小时。后续请求需在HTTP头部携带令牌：`Authorization: Bearer <token>`。服务器解析令牌获取用户信息，验证权限后处理请求。

刷新令牌机制用于延长会话时间。访问令牌到期前，客户端可使用刷新令牌获取新的访问令牌，避免频繁登录。刷新令牌有效期为7天，存储在refresh_tokens表中。

### 3.6.2 权限控制策略

基于角色的访问控制（RBAC）实现了权限管理。users表的role字段标识用户角色（admin、expert、user），每个角色对应一组权限。

管理员拥有所有权限；应急管理人员可以进行风险评估、预警发布、监测管理，但不能修改系统配置；普通用户只能查看数据和提交报告。权限检查在中间件层实现，每个需要权限控制的接口前置权限验证逻辑。

### 3.6.3 数据安全措施

密码使用bcrypt算法加密，加盐后哈希值存储到password_hash字段，不保存明文。数据库查询采用参数化语句，防止SQL注入攻击。文件上传限制文件类型（仅允许jpg、png格式图片）和大小（最大5MB），验证文件头信息，防止恶意文件。

操作日志记录到user_login_logs表，包含登录时间、IP地址、操作类型，便于安全审计。
